# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Zinject is a lightweight dependency injection container for Swift, built using Swift Package Manager. It provides thread-safe service registration and resolution with configurable scoping.

## Development Commands

### Building and Testing
- Build: `swift build`
- Test: `swift test`
- Test specific target: `swift test --filter ZinjectTests`
- Race detection: `swift test --sanitize=thread` (expected clean; a report here means a real ordering bug, not a false positive). The exit tests skip themselves under TSan — a `processExitsWith` child dies at startup because TSan's interceptors are not installed in it, and since almost all of them expect `.failure`, they used to *pass* under TSan without running
- Metrics build: `swift test -Xswiftc -DZINJECT_METRICS` — compiles in `Container.metrics`
- Section-contract checks in a release build: `-Xswiftc -DZINJECT_BORROW_CHECKS` (the flag keeps its old name) — on by default in debug, so `swift test` already has them. Only the two *nested-read* `InsideABorrowTraps` tests are compiled where the checks are: without them those tests perform the real violation. The two nested-*write* ones are not gated, because the cells refuse a nested write on their own in every build, and that is what those two now pin. So `swift test -c release` runs 115 tests and `swift test -c release -Xswiftc -DZINJECT_BORROW_CHECKS` runs all 117
- Benchmark: `swift run -c release ZinjectBench` — release mode is required for meaningful numbers
- Benchmark one strategy as the process default: `ZINJECT_CONCURRENCY=unfairLock swift run -c release ZinjectBench`

### Package Management
- Resolve dependencies: `swift package resolve`
- Generate Xcode project: `swift package generate-xcodeproj`

## Architecture

### Core Components

- **Container**: Main DI container implementing `Resolver` protocol. All mutable state lives in one nested `Container.State` struct (a single `ServiceTable`) held in whichever `StateCell` the container was constructed with. `resolve` and everything it touches on the cached path are `@inlinable`/`@usableFromInline` — see "Working on the resolve fast path". It also has `withResolvedRequired(_:_:)`, which lends a class instance instead of returning one — deliberately on `Container` and not on `Resolver`, since the only default implementation the protocol could offer would retain, and the existential cannot benefit anyway
- **ConcurrencyStrategy** (public): Selects the cell at `Container` init — `.leftRight` (default), `.recursiveLock`, `.unfairLock`. `Container.defaultConcurrency` is a process-wide default seeded from the `ZINJECT_CONCURRENCY` environment variable, so a real app can A/B strategies without a recompile. The whole point is to gather real-world data on whether Left-Right is worth its cost
- **StateCell** (internal): The protocol both implementations satisfy — `read` takes `(UnsafePointer<Value>) -> R`, `write` takes `(inout Value) -> R`, plus a `rethrows` `read` overload for `withResolvedRequired`. Its doc comment is the *union* of both implementations' contracts (pure write bodies, short non-reentrant read bodies), because the implementation is a runtime choice
- **LeftRight** (internal): A `StateCell` for read-mostly data — two copies of the state, wait-free readers, writers that apply each change twice with a drain in between
- **MutexCell** (internal): A `StateCell` that serializes everything behind one lock, generic over a `Locking` protocol with two conformers, `RecursiveLock` (`NSRecursiveLock`, the historical baseline) and `UnfairLock` (`os_unfair_lock`, `NSLock` off Darwin). `Locking` is a generic parameter rather than an existential so it specializes away — a dispatch cost paid by one arm and not the other would be indistinguishable from a design difference
- **ZinjectDiagnostics** (public): `slotlessReads` / `threadsWithoutSlot` / `readerSlotCapacity`. Non-zero `slotlessReads` means `.leftRight` is running *worse* than `.unfairLock` in that process. Both counters sit on already-slow paths, so the fast path is unchanged
- **ContainerMetrics** (public, `#if ZINJECT_METRICS`): Per-container resolve/write tallies. Compiled out by default because collecting them adds an atomic increment to the resolve fast path
- **ReaderRegistry** (internal): Process-global pthread-TLS allocator handing each thread a small integer, used to index per-thread read-indicator slots. Fixed capacity (64); threads past it fall back to the writer lock. It also publishes `allocatedSlotMask()`, the bit set of IDs live threads currently hold, which is what bounds a `LeftRight` drain — capacity is therefore tied to `UInt64.bitWidth`
- **ResolutionStack** (internal): Per-thread pthread-TLS stack of in-flight resolutions, tagged by container, for cycle detection. Also carries `openSection`, the one slot `SectionGuard` needs — same thread, same kind of fact, and one fewer pthread key
- **SectionGuard** (internal): Traps on a container operation performed while this thread holds a read or write section open. The rule it encodes is that one, not "nothing inside a `withResolvedRequired` body" — that body is today's only way to reach the state, not the state itself, so whatever later holds a section across user code arms this same guard instead of inventing a second rule. Exists because the mistake fails *differently* under each strategy, and the strategies are supposed to be indistinguishable. Compiled out unless `DEBUG || ZINJECT_BORROW_CHECKS`, which is affordable only because it now covers the *loud* half of the mistake: a nested read, which works under two strategies and aborts under the third. The silent half — a nested write — is refused by the cells themselves in every build (see below)
- **ConstructionToken** (private, `Container.swift`): One per `.container`-scoped key whose factory is running. The thread that installs it constructs; others wait on its `NSCondition`. A thread that finds its *own* token has re-entered its own construction — that is a cycle, not a race — so it must fall through rather than wait, letting `pushResolutionStack` trap with the rendered chain. The token map lives behind its own `NSLock`, deliberately outside `Container.State`: installing a token is not a pure function of the state (a Left-Right write body would run it twice and get two different answers), and routing cold resolves through a cell write would drain every reader slot to synchronize data no reader reads. It is also what keeps construction semantics identical under all three strategies
- **Resolver**: Protocol defining service resolution interface; also provides `resolveRequired(_:)` (traps on missing registration)
- **ServiceFactory**: Internal factory pattern for service creation with scope management; `create` and `runInitCompleted` are separate so the container can cache instances before callbacks run. Class-constrained (`AnyObject`) so registrations can be compared by identity. `requiresMainActor` lets `resolveAsync` hop only where needed
- **Scope**: Enum defining service lifetimes (`.transient`, `.container`)
- **ServiceKey**: Type-based key for registration/resolution. Carries the type's metadata pointer as raw bits (`raw`), which is what the table hashes, probes, and compares
- **ServiceTable** (internal): Flat, open-addressed, power-of-two map from `ServiceKey` to registration and cached instance, replacing the two `Dictionary`s. Parallel columns, deliberately: a cached resolve touches only `keys` and `instances`, neither of which is reference counted, so the read path does no ARC at all. `owners` holds the storage alive and is touched only by writers. Deletion rebuilds the table rather than back-shifting a cluster — `unregister` is a teardown operation, and the simplest correct implementation is the right one there
- **CachedInstance** (internal): Owns one cached instance in manually allocated, `Service`-typed memory, so a resolve loads it with a typed load instead of casting out of `Any`. Its doc comment carries the lifetime argument — why dropping the owner inside a write is always safe against a concurrent reader — and that argument is what makes the bare pointer in `ServiceTable.instances` legitimate
- **InstanceBuffer** (internal): Six-word staging buffer a cached instance is copied into inside the read section and moved out of afterwards. It exists so the read body names no `Optional<Service>`: in a caller that did not specialize, allocating one costs a `swift_getGenericMetadata` per resolve (~35 ns). Services too large or too aligned for it take `Container.resolveOversized`. It stages two different things now — the instance for `resolve`, the body's result for `withResolvedRequired` — for the same reason on different type parameters

Depends on `apple/swift-atomics` for the atomics the Left-Right algorithm needs.

### Key Patterns

- Services are registered with factory closures: `container.register(Type.self) { resolver in ... }`
- Distinct `register` (`@Sendable` factory) and `registerMainActor` (`@MainActor` factory) methods; a main-actor factory runs inline on the main thread and **traps** off it. `resolveAsync(_:)` is the supported off-main path — it `await`s a main-actor hop only when the registration needs one and nothing has constructed the service yet. It replaced a `DispatchQueue.main.sync` hop that deadlocked whenever main was waiting on the caller, and that only reproduced on a cache miss
- Fluent API for configuration: `.scope(.container)`, `.initCompleted { ... }` (multiple callbacks accumulate)
- Recursive dependency resolution through resolver parameter in factories; circular dependencies are detected via a per-thread resolution stack and trap with a descriptive message. A cycle realized only *across* threads (thread 1 inside A's factory resolving B, thread 2 inside B's factory resolving A) hangs on the construction gate instead of trapping — the wait graph follows dependency edges, so this is possible only for a dependency cycle, which is already a programmer error the single-threaded case traps on
- Re-registering a type evicts its cached instance; `unregister(_:)` and `removeAll()` provide teardown
- No lock is held while user code (factories, `initCompleted`) runs. A `.container`-scoped service is nonetheless constructed **exactly once** under a concurrent first resolve, because construction is serialized per key by a `ConstructionToken` rather than by the state cell — a slow factory for one type never blocks resolving another. `Container.publish` keeps its superseded case anyway, so "only one instance is ever handed out" does not depend on the gate for correctness
- A resolve whose registration was replaced or removed while its factory ran returns its instance but does not cache it, checked by factory identity in `Container.publish`
- `.transient` resolves deliberately skip the write path entirely, and are not gated by a `ConstructionToken`; routing them through a Left-Right write would drain every reader slot twice per resolve, and serializing their construction would defeat what transient means
- `withResolvedRequired(_:_:)` lends a `.container`-scoped class instance for the duration of a closure without touching its reference count, instead of returning an owned reference. It exists because that retain/release pair — not anything in the container — is what makes a shared singleton resolved from every core the one read row `.leftRight` loses; lending wins it back by ~960x at 16 threads, and never costs anything at one. Three things about it:
  - **The body runs inside the read section, where the container is not re-entrant.** A `resolve` or `register` from a body spins forever under `.leftRight`, aborts under `.unfairLock`, and frees the instance being borrowed under `.recursiveLock`. `SectionGuard` makes all three trap in debug builds. In release, a nested *write* still traps — the cells catch that themselves — and a nested *read* is undefined behaviour, documented as such. The natural body is a method call on the resolved service, so a service that lazily resolves its own dependencies is a deadlock written by accident
  - **Escaping the value is safe; escaping an address would not be.** Assigning the borrowed instance anywhere copies it, which retains, and the caller gets an ordinary owned reference. The API hands out no addresses, which is the whole difference between this and an `Unmanaged`-returning accessor
  - **Classes only, and that costs nothing** — a struct has no reference count, so it never had this problem
- All strategies must be behaviorally indistinguishable from outside the container. Anything a test can observe has to hold for all three, or `ConcurrencyStrategy` is not a legitimate runtime choice

### Working on the resolve fast path

The cached path is about 4 ns of work, and every piece of that was bought with a measurement. Before changing it, know what each piece costs, because the obvious simplifications each cost more than the whole path:

- **`Dictionary` costs ~13 ns per lookup.** `Hasher` is SipHash-1-3 over a per-process seed. `ServiceTable` exists because a type-metadata pointer needs one multiply, not a cryptographic hash
- **`as?` out of an `Any` costs ~7 ns** in `swift_dynamicCast`, which is why instances are stored typed
- **A generic that cannot specialize costs ~35 ns *per resolve*** in runtime metadata instantiation. This dominates everything else on this list. It is why `resolve` is `@inlinable` — measured cross-module, the same resolve ran at 69 ns unspecialized and 4 ns specialized — and why the read body stages through `InstanceBuffer` rather than assigning to a `Service?` local, which reintroduces the cost for any caller that did not specialize (`any Resolver`, generic code)
- **A retain on a shared instance costs ~600 ns at sixteen cores**, against ~1 ns uncontended. Nothing else on this list scales with core count, which is why it dominates once anything is shared. `withResolvedRequired` exists to not perform one

The metadata rule is *dependent layout*, not genericity, and getting that wrong in either direction is expensive. `Optional<Service>` has a size and tag encoding that depend on `Service`, so an unspecialized frame must ask the runtime for its metadata to allocate one — that is the 35 ns. A bare `Service` or `Result` is free: its metadata is already an argument to the function, so sizing it is a value-witness field load. `InstanceBuffer` is concrete and therefore free at any specialization. So "no generics in the read body" is both wrong and unusable as a rule; "name no type whose layout depends on a type parameter" is the real one.

That is the trap: this code looks like ordinary Swift, and ordinary Swift changes to it — an enum carrying the instance, an `Optional` local, a helper returning `Service?` — silently reintroduce metadata instantiation on paths that no longer specialize. Anything touching the read body needs a benchmark run of the *unspecialized* path, not just the bench's tables.

There is a second trap of the same shape on the borrow path, and it is worse because it looks like the obvious code. `body(storage.assumingMemoryBound(to: Service.self).pointee)` is `+0` only when `body` inlines and ARC can see that nothing frees the instance across it. Against an opaque call — which is what a real body is — the compiler must keep the loaded `Service` alive itself, and puts back exactly the retain/release pair the API exists to remove. Measured, that is 300x: 1.6 M ops/sec versus 479 M with sixteen cores on one singleton. `Container.borrowCachedInstance` therefore never loads a managed `Service` at all; it reads the reference as a raw pointer and hands it over through `Unmanaged._withUnsafeGuaranteedRef`. The underscore is load-bearing, and the `isBareReference` size check is what keeps the raw-pointer load honest.

Removing an `@inlinable` or `@usableFromInline` annotation is a performance change, not a cleanup.

### Working on the concurrency code

`Container` reaches its cell through `readState`/`writeState`, which switch on an internal `enum Storage` of concrete cells. **Do not replace that with `any StateCell<State>`** — the existential puts a witness-table call on the resolve fast path and stops the cell's read from inlining, a cost paid by every strategy equally, which is exactly what would make the strategies impossible to tell apart. That defeats the reason the abstraction exists.

`LeftRight` is small but every line of it is load-bearing. Before changing it, read the type-level documentation in `Sources/Zinject/Internal/LeftRight.swift`; the parts that most look like redundancy are not:

- `activeInstance` and `activeIndicator` are **separate** atomics. Collapsing them into one variable breaks the algorithm
- `toggleIndicatorAndWait` drains **twice**, before and after switching indicators. Both drains are required
- A drain scans the reader IDs in `ReaderRegistry.allocatedSlotMask()`, not all 64 slots — that was ~715 ns of a first resolve. It must stay the *live* set: a high-water mark would be permanently raised by one thread-pool spike, process-wide, for every container. The soundness argument is written out above `waitUntilDrained` and depends on the mask load being sequentially consistent and on bits being published before a reader can arrive
- The reader's arrival and its load of `activeInstance` must stay `.sequentiallyConsistent`, as must the writer's drain load — they form one total order. The other orderings are deliberately weaker and are commented with why
- Write closures run **twice** and must be pure functions of the state passed in
- Read closures must be short, non-blocking, and must never call back into `write`
- `writerLock` is an `NSRecursiveLock` and must stay one. It guards the slotless read fallback as well as writers, and a reader holding a slot can nest a read (its counter goes to two), so a reader without one has to be able to as well. With a plain `NSLock` that nesting deadlocked, which made whether nesting worked a function of the process's thread population — safe at sixteen live readers, a hang at a hundred and twenty-eight. It costs the fallback path 12–25% against `NSLock`, measured; the fast path never touches this lock. Removing the cliff outright rather than making it recursive is what an overflow pool of shared counters in `ReaderRegistry` would do, and is the better end state

**A write nested inside this thread's own read section traps, in every build.** It is the one contract clause the cells enforce themselves rather than leaving to `SectionGuard`, because its symptoms are silent: an endless spin under `.leftRight` (a spin, not a blocked thread, so no deadlock detector sees it) and a mutation under a live reader's pointer under `.recursiveLock`. Three checks, all off the fast path:

- `waitUntilDrained` traps when the counter refusing to clear belongs to the calling thread. That is proof rather than heuristic — nobody else can touch that counter — and it costs one thread-local read per drain. It uses `ReaderRegistry.assignedID()`, not `currentID()`: a thread that only writes must not be handed a reader slot for having asked
- `LeftRight.write` traps when the calling thread re-entered `writerLock` from a slotless read. This is what closes the hole that making the lock recursive would otherwise open — a slotless reader announces itself in no indicator, so the drain would find nothing and the second application would land on the copy the enclosing read is holding
- `MutexCell.write` traps on a non-zero `readDepth`, guarded by `Locking.isRecursive` so the branch and the field vanish from the `os_unfair_lock` arm, which aborts on its own before any check could run — with no stderr, as a kill with a crash-report reason

Both depth counters live behind `UnsafeMutablePointer`, not in stored `var`s. A class's stored properties carry *dynamic* exclusivity enforcement, and mutating one twice per read cost `.recursiveLock` 18% of its single-threaded cached resolve. `MutexCell.storage` was already behind a pointer for the same reason.

The traps call `fatalError`, not `precondition`. The standard library discards a `precondition` or `preconditionFailure` message outside a debug build — in release it lowers to a `condfail` carrying the fixed string "precondition failure" — so a release trap would print nothing, and most of the point is that whoever reads the crash log can tell what they did. `fatalError` also survives `-Ounchecked`, which is right here: the alternative to trapping is not a slightly slower program.

Each cell has **two** `read` methods: the non-throwing one, and a `rethrows` overload that `withResolvedRequired` needs so a caller's body can throw. Do not fold them into one. A `rethrows` function is compiled with a throwing convention, and the non-throwing `read` is on `resolve`'s path — this is a performance change, not a tidy-up. Both are correct on an unwind for the same reason: the reader's departure and the mutex's unlock are `defer`red, so a throw is just an early exit. Under `.leftRight` a leaked arrival would make the *next write* hang forever, which is why the test for it asserts on a `register` after the throw rather than on the throw itself.

The read contract now binds the library's users, not only its authors: `withResolvedRequired` runs arbitrary user code inside a read section. "Short and non-blocking" is the same requirement it always was, but it is now a documented API contract with a guard behind it (`SectionGuard`) rather than a note to ourselves.

**The library is model A: sections are closed around user code.** `resolve` closes its read section before running a factory, so a factory that resolves its own dependencies re-enters with nothing held. That is what keeps all three strategies valid, and the matrix is in `ConcurrencyStrategy`'s doc comment so that a reader meets the constraint before the throughput table, which on its own points at `.unfairLock`. Model B — sections held open across user code — is not an unturned knob: a thread cannot hold a grace period open and wait for all grace periods to close, so `.leftRight` cannot implement it at any lock's re-entrancy, and choosing it would mean deleting `ConcurrencyStrategy` and keeping `.recursiveLock`.

### Test Structure

Tests use Swift Testing framework (`import Testing`) with `@Test` attribute. Test classes A, B, C demonstrate dependency chains and scoping behavior.

- `ZinjectTests.swift` — container behavior, scopes, `initCompleted`, main-actor factories, cycle detection, and the concurrency tests that pin observable resolve semantics. Everything semantically interesting is `@Test(arguments: ConcurrencyStrategy.allCases)`. The `processExitsWith` tests cannot be — that closure runs in a spawned process and so must not capture — and do not need to be: the two cycle tests exercise `ResolutionStack`, and `mainActorSyncResolveOffMainTraps` exercises `MainActorServiceFactoryImpl`, none of which touch a cell. Tests that synchronously resolve a `registerMainActor` registration are `@MainActor` because the off-main path traps by design; `resolveAsync` is what the off-main tests use
- `ConcurrencyStrategyTests.swift` — the selection plumbing: `ZINJECT_CONCURRENCY` parsing, `Container.defaultConcurrency`, and that the mutex strategies never touch a reader slot. The last two ask a freshly spawned thread what slot it ended up with rather than diffing `ZinjectDiagnostics.slotlessReads`. That counter is process-global and the suite runs in parallel, so the tests that exist to take the fallback failed these at random — about one run in eight
- `StateCellTests.swift` — the three cells proved interchangeable at the primitive level, including that all three now refuse a write nested inside a read. Generic over the cell rather than parameterized by value, since `StateCell` has an associated type and the tests construct one. The two that trap assert on the *message*, not the exit status: before the trap existed the same mistake failed by hanging, and an exit-status check is satisfied by any way of dying
- `ServiceTableTests.swift` — the table on its own: probing, growth through two resizes, the rebuilding delete, and that dropping an entry frees its instance storage. It also pins that a table is a value, since Left-Right copying `State` is exactly that
- `LeftRightTests.swift` — the algorithm on its own: convergence of the two copies, readers never observing a partially applied write, writer progress under sustained read load, over-capacity readers taking the fallback, reader-ID assignment and recycling, and that a read nests on the slotless path. That last one is tested twice on purpose — directly through `readWithoutSlot`, which is deterministic and leaves the shared slot pool alone, and once for real in a spawned process, because occupying all 64 slots in-process makes every test running beside it take the fallback and fail

`ZinjectTests.swift` also covers the instance-storage shapes the fast path is sensitive to — oversized services that take `resolveOversized`, protocol-typed registrations (an `any P` is five words, which is why `InstanceBuffer` is six), structs holding references, and that eviction actually releases the cached instance under every strategy.

Its borrowed-resolution tests pin what a test suite *can* pin, and the boundary matters. They cover that a borrow lends the instance `resolve` would return, constructs once through the same `ConstructionToken` gate under an 8-way race, runs `initCompleted`, rebuilds a `.transient` every time, tallies in metrics identically, survives a throwing body, and leaves no *unbalanced* retain (a weak probe that must go nil on `removeAll`). They cannot pin the absence of a *balanced* retain/release pair, which is the property the API is for: `CFGetRetainCount` is Darwin-only and unreliable, and `isKnownUniquelyReferenced` only separates one reference from more — useless here, since the container always holds one, so the good case is two and the bad case is three. That property is pinned by the benchmark, at roughly 900x, and a comment above the tests says so. Same division of labour `InstanceBuffer` already lives under.

Two things there are less load-bearing than they look. The `.transient` test escapes both instances rather than comparing `ObjectIdentifier` inside the bodies, because nothing retains a transient instance past its body — the first is freed on the way out and the second allocation lands at the same address, so identity of a dead object proves nothing. And `isBareReference` has no reachable failing case today: this toolchain rejects `withResolvedRequired((any ClassGreeter).self)` outright, since a class-bound existential does not satisfy `Service: AnyObject`. The check is kept because it folds away when specialized and encodes a property of the representation rather than of what the type checker currently admits, and its test asserts the predicate directly instead of pretending to reach the branch.

The `ZinjectBench` target still vendors a private copy of the pre-rewrite `NSRecursiveLock` container as `LockedContainer`. Keep it: `.recursiveLock` goes through `ServiceKey`, `ServiceFactory`, scope lookup, and the resolution stack, and measures roughly 7x the `register` cost of the vendored one for exactly that reason. Only `LockedContainer` isolates the strategy change from everything else the container has grown.

Its tables are ordered to answer four separate questions, and conflating them is how this gets misread: cached-resolve throughput says which strategy reads fastest; write-side, composition-root, and thread-population tables say whether an application performs that operation often enough, and on few enough threads, to collect; the two borrowed-resolve tables say what returning an owned reference costs rather than lending one. It also measures bare `retain`/`release` contention with no container involved, which is what explains the shared-singleton row rather than anything in `Container`.

#### What the shared-singleton row actually is

The class-typed shared-key row is the only read row `.leftRight` loses, and it has been attributed rather than guessed at. Do not re-derive this:

- **It is the retain, and only the retain.** Lending the instance instead of returning it takes that row from 1.6 to 1913 M ops/sec at sixteen threads. The cell was never involved — the value-typed row, same container and no refcount on the result, runs at ~2000 M ops/sec on the same cores
- **It is not fence placement.** Moving the retain out of the read section, so it no longer sits between the reader's sequentially-consistent arrival and its departure, changes nothing (1.6 → 1.6). That was the plausible hypothesis and it is wrong
- **The mutex arms win it by convoying, not by being faster.** They perform the same retain, but inside a critical section, so each one finds the cache line already exclusive. Move the retain outside `.unfairLock`'s critical section and it collapses from 44 to 1.6 — precisely `.leftRight`'s number. This is why `arcBaseline` has a serialized column, and why that column is *faster* than its unsynchronized one past four threads
- **`.leftRight` running below the bare unsynchronized ARC baseline is expected**, for the same reason: nothing paces the contention

The `+work` companion table exists because the bare one overstates. Sixteen cores touching one line back to back with nothing in between is not a workload; contention falls off sharply once accesses are spaced out. With 21 ns of work per call the win is 297x rather than 963x — still decisive, but the two tables are a pair and reading either alone gets the wrong answer in opposite directions.
